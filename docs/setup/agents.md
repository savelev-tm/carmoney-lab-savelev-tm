# Роли агентов

## Planner

Основной агент предназначен для изучения проекта и составления плана.
По заданной конфигурации должен изменять файлы только в docs/plan/.
Запуск команд через bash запрещён.
Для поиска фактов может обращаться к субагенту scout.

### Проверка ограничения на редактирование

Planner попытался штатным инструментом edit добавить комментарий в backend/public/index.php.

Kilo отклонил вызов на уровне разрешений проекта:

{"permission":"edit","pattern":"*","action":"deny","source":"project"}

По сообщению агента, файл backend/public/index.php не изменился. Обходные пути не использовались.

Вывод: наличие инструмента edit в наборе агента не означает разрешения применять его к любому файлу. В этом эксперименте запрещённая правка backend была остановлена permission-слоем Kilo.

Эта проверка подтверждает запрет конкретной правки. Она не подтверждает, что planner может сохранять планы в docs/plan/: разрешение записи в эту папку нужно проверять отдельно. Запрет bash в представленном фрагменте также не проверялся.

## Scout

Субагент-разведчик предназначен для поиска фактов в коде.
Должен возвращать пути файлов, номера строк и краткие пояснения.
Редактирование файлов и запуск команд через bash запрещены по заданной конфигурации.

## Подтверждение вызова scout

В предоставленном фрагменте виден запрос с упоминанием @.kilo/agents/scout.md и ответ с результатами поиска.

Отдельная карточка вызова субагента или запись о делегировании planner → scout не представлены. Поэтому по этому фрагменту подтверждён результат поиска, но не подтверждён запуск scout именно как отдельного субагента: упоминание файла могло только добавить его содержимое в контекст текущей сессии.

## Вывод

Эксперимент с planner показал срабатывание технического ограничения: permission-слой Kilo отклонил попытку редактирования backend/public/index.php.

Поиск scout дал карту обработки пробега: входные данные, валидация, сохранение и чтение из БД, а также связанные настройки и тесты.

Для полного подтверждения работы ролей остаётся отдельно показать разрешённую запись planner в docs/plan/ и фактический вызов scout как субагента. Ограничения scout на edit и bash этим ответом поиска не проверены.

## Автоматическое делегирование

Запрос отправлен в новой сессии planner без @scout:

«Найди все места в проекте, где читается пробег автомобиля (mileage). Верни пути, номера строк и краткое объяснение каждого места. Файлы не меняй».

Результат: planner искал самостоятельно. В предоставленном логе вызов scout не зафиксирован.

Наблюдение: planner определил запрос как поисковую задачу, но решил выполнить её сам. По логу он искал упоминания mileage, mileage_km и «пробег», изучал соответствующие файлы и подготовил ответ с путями, номерами строк и пояснениями.

При поиске агент обнаружил предыдущий отчёт scout в docs/setup/agents.md. Он использовал его для сопоставления с исходниками, а не как результат нового вызова субагента. Чтение сохранённого отчёта не является делегированием.

Planner сообщил, что файлы не изменялись. Он также не создавал план, поскольку запрос требовал только поиска информации.

Вывод: автоматическое делегирование в этом запуске не произошло. Наличие scout и возможности поручать ему поиск само по себе не гарантирует его вызова. Если делегирование обязательно, это нужно явно закрепить в инструкциях planner и подтвердить новым экспериментом по фактическому вызову субагента.
