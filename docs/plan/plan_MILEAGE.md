# plan_MILEAGE — правило «пробег не больше 400 000 км, иначе review»

План до кода (1.4.3). Сверен с `docs/setup/code_map.md`, отчётом scout из
`docs/setup/agents.md` и чтением исходников на 2026-09-27; номера строк — по
текущему состоянию репозитория. Исходники, конфиг и тесты при составлении плана
не менялись. В плане нет кода, кроме сигнатур.

Подход: «пробег высокий → review» — правило **решения**, а не валидации
(обоснование — `docs/setup/code_map.md`, раздел «Куда встанет правило»),
поэтому расширяется `DecisionEngine` — единственный производитель решения.
Альтернатива (пост-обработка результата в `AssessmentService::assess()`,
строка 33) отклонена: логика решения расползается по двум классам, а порог всё
равно пришлось бы куда-то инъектить.

## 3. Тесты

Чтобы изолировать правило пробега, LTV во всех кейсах фиксируется в
approve-зоне (50.0; на уровне сервиса — payload 450000 при market_value
900000). Кейсы границы — в `DecisionEngineTest`, те же значения интеграционно —
в `AssessmentServiceTest` (проверяется и `approved_limit`).

- Ниже границы — 399999: правило не срабатывает; `decide(50.0, 399999)` → `approve`, на уровне сервиса `approved_limit` равен запрошенной сумме. Определено формулировкой «не больше 400 000 км».
- Ровно на границе — 400000: правило не срабатывает («не больше» — включительно, 400000 проходит); `decide(50.0, 400000)` → `approve`. Определено формулировкой; тест ловит случайную замену строгого сравнения на нестрогое.
- Выше границы — 400001: правило срабатывает; `decide(50.0, 400001)` → `review`, на уровне сервиса `approved_limit = 0`. При LTV ≤ 85 — определено («иначе решение review», review-зона тем более остаётся review); при LTV > 85 — **не определено требованиями**, вопрос Q1: `decide(90.0, 400001)` → `review` или `reject`? До ответа кейс не пишется — фиксировать предположение тестом нельзя.
- Пустой пробег:
  - ключ `mileage` отсутствует или равен `null` → `ValidationException` → HTTP 422 «Пробег от 0 до 500000 км» (`ApplicationValidator`, строки 43–45: `null`/отсутствие превращаются в −1, что меньше нуля). Существующее поведение, фича его не меняет; тест закрепляет его на уровне сервиса (`assess()` бросает исключение).
  - `mileage: ""` (пустая строка) → приводится к 0, проходит валидацию как 0 км, решение считается без участия правила. Ожидаемое поведение **не определено требованиями**: существующий код даёт «0 км», но «пустое значение» интуитивно ждут ошибкой — вопрос Q2. До ответа тест не пишется.

Дополнительно — защита от ложного вывода «пробег прошёл проверку ⇒ заявка
одобрена»: кейс `decide(90.0, 1000)` → `reject` на уровне движка
(прохождение проверки пробега — не достаточное условие approve); на уровне
сервиса это уже покрывает существующий `testRejectsHighLtv` (mileage 96000,
LTV 95.0) — он остаётся зелёным без правок.

## 4. Риски

- Взаимодействие с существующей проверкой `vehicle.max_mileage_km` (500000, валидация): порогов становится два с разной семантикой — 400000 управляет решением, 500000 даёт 422. Рабочая зона нового правила — 400001…500000; всё, что выше 500000, до `decide()` не доходит. Риск: случайно использовать в движке `max_mileage_km` вместо нового ключа — правило станет мёртвым кодом; это ловится кейсом 400001 → review. Сами 500000 и текст ошибки валидации не менять.
- Смена сигнатуры `decide()`: известных вызовов два — `AssessmentService` (строка 33) и `DecisionEngineTest` (строка 23), плюс инъекция конструктора в `AppFactory` (строка 37); других мест нет (проверено поиском по репозиторию). Дефолтного значения у `$mileage` не будет — рассинхрон сигнатур упадёт сразу.
- Ловушка `<`/`<=` в `decide()` (строка 32): докблок обещает «`LTV <= approve_max -> approve`», а код проверяет строгое `<`, поэтому LTV ровно 60.0 даёт `review` (расхождение зафиксировано в `code_map.md`). Соблазн «заодно починить» это при правке метода — вне задачи: для LTV 60.0 это бизнес-изменение review → approve, которого нет в требовании, и его не поймает ни один существующий тест (в провайдере нет значения 60.0). Не трогать.
- Приоритет с `reject` (Q1): буквальное прочтение «иначе решение review» понизит reject при LTV > 85 до review для авто с большим пробегом — смягчение отказа; консервативное прочтение ограничивает только approve, оставляя reject. Оба варианта нельзя выбирать за заказчика; ошибка в любую сторону — бизнес-риск. Выбор изолирован одним условием (шаг 6), чтобы ответ менял минимум кода.
- `approved_limit` и форма ответа API не меняются: при review лимит остаётся 0 (`AssessmentService`, строка 39), фронтенд рисует решение как раньше.
- Уже сохранённые заявки не пересчитываются: решение пишется в таблицу `decisions` при создании заявки (`ApplicationRepository::save()`, строки 49–58); правило действует только на новые расчёты.
- Ожидания существующих тестов менять ради зелёного `make test` запрещено (AGENTS.md); обновление `DecisionEngineTest` — только под сигнатуру, ожидания LTV-кейсов сохраняются.
- Пустая строка → 0 км — существующее поведение, фича его не ухудшает, но приёмка «пустого пробега» (Тесты) вскроет его; тестом не закреплять ни один вариант до ответа на Q2.

Не входит в задачу: фронтенд (`frontend/`), БД (`db/schema.sql`, `db/seed.sql`)
и миграции, `ApplicationValidator` и тексты ошибок 422, значение
`vehicle.max_mileage_km`, HTTP-слой (форма ответов), LOAN-12 (лимит по
`ltv_by_age`), пересчёт старых заявок, исправление расхождения докблока и кода
`DecisionEngine`, feature-тесты через HTTP, обновление `docs/setup/code_map.md`
и README.
