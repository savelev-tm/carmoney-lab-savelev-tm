плана писалась до спеки), `docs/intent/intent_MILEAGE.md`,
`docs/setup/code_map.md` и повторным чтением исходников на 2026-09-28;

над планом не менялись; в плане нет кода, кроме сигнатур.

- Q1 (приоритет с `reject`) закрыт: правило ограничивает только `approve`,
  исходы `review` и `reject` не меняются (REQ-MILEAGE-01, AC-MILEAGE-04/05).
  Отменено «кейс не пишется до ответа»: кейсы пишутся как guards.
- Q2 (пустая строка) закрыт: `""` → HTTP 422 (REQ-MILEAGE-02, AC-MILEAGE-06).
  В плане появились красный тест и правка `ApplicationValidator` — в версии 1
  правки валидатора не было вовсе.
- Q4 (признак причины review) закрыт: не входит, форма ответа API не меняется.
- Q3 (имя и место ключа конфига) остаётся открытым (спека, Open questions 1),
  но неблокирующим: план работает с рабочим именем
  `vehicle.review_mileage_threshold_km`.
- Текст ошибки 422 для `""` остаётся открытым (спека, Open questions 2):
  рабочее решение — переиспользовать существующий текст; тесты к тексту не
  привязываются.
- Добавлены границы 500 000 / 500 001 (AC-MILEAGE-08/09), которых в версии 1
  не было. Снято требование «все новые тесты сначала красные»: красными по
  построению бывают только тесты отсутствующего поведения; guards зелёные с
  самого начала, и это их назначение — зафиксировать существующее поведение
  до реализации.

## Как задача встраивается в существующие проверки

Подход прежний (обоснование — `docs/setup/code_map.md`, «Куда встанет
правило»): «пробег высокий → review» — правило **решения**, живёт в
`DecisionEngine` (единственный производитель решения); пустая строка —
правило **валидации**, живёт в `ApplicationValidator`. У пробега становится
два порога с разной семантикой:

1. `vehicle.max_mileage_km` = 500000 (`backend/config/rules.php:23`) —
   существующая граница валидации: `ApplicationValidator` (строки 43–46),
   нарушение → `ValidationException` → HTTP 422 в контроллере (строки 27–31
   и 58–62), решение не считается. Не меняется (REQ-MILEAGE-03).
2. Новый порог 400 000 — порог решения: срабатывает только после успешной
   валидации, в рабочей зоне 400 001…500 000; понижает `approve` до
   `review`. Значение 500 000 проходит валидацию и триггерит правило
   (AC-MILEAGE-09); 500 001 отсекается валидацией до правила (AC-MILEAGE-08).
   Класть это правило в валидатор нельзя: нарушение даёт `review`, а не 422.

Взаимодействие с исходами по LTV (пороги не меняются: approve < 60.0,
review ≤ 85.0 включительно, reject > 85.0 — `rules.php:43–46`):

- `approve` (LTV < 60.0) и пробег > 400 000 → `review`, `approved_limit` = 0
  (`AssessmentService:39`) — единственный меняющийся путь (AC-MILEAGE-03/09).
- `review` (60.0 ≤ LTV ≤ 85.0) при любом пробеге — без изменений
  (AC-MILEAGE-05).
- `reject` (LTV > 85.0) при любом пробеге — без изменений (AC-MILEAGE-04).
  Чтобы приоритет «правило ограничивает только approve» выполнялся
  конструкцией, проверка пробега вкладывается в approve-ветку `decide()`,
  а не ставится перед ней.
- Правило действует только на новые расчёты: нормализованный пробег уже
  сохраняется в БД (`ApplicationRepository:45`); пересчёт старых заявок не
  входит (спека).

Пустая строка пробега: сегодня `(int)"" === 0`, а 0 — валидный пробег,
поэтому `""` молча проходит как 0 км. Пробег — единственное числовое поле с
таким поведением: у `year`, `market_value`, `requested_amount`, `term_months`
пустая строка превращается в 0, который выпадает из их диапазонов, и они уже
сегодня дают 422. После правки `""` отклоняется до расчёта решения
(AC-MILEAGE-06); `null`/отсутствие ключа и так дают 422 «Пробег от 0 до
500000 км» (сентинел −1, `ApplicationValidator:43–46`, AC-MILEAGE-07).
Фронтенд правок не требует: `Number('') === 0` (`frontend/app.js:14`), форма
отправляет пустое поле как `0`, а не `""`; контракт меняется только для
прямых API-клиентов.

## 2. Шаги

Этап 1 — тесты, выявляющие отсутствие поведения. Код не трогается.

1. `DecisionEngineTest` — кейсы из раздела «Тесты» с целевой сигнатурой
   `decide(float $ltv, int $mileage)`. Механика красного: текущая сигнатура
   `decide(float $ltv)` лишний аргумент молча игнорирует (PHP допускает
   лишние аргументы у пользовательских методов), поэтому кейсы выполняются
   и падают именно на утверждении — `approve` вместо `review`. Это
   выявление отсутствующего поведения, а не сломанный тест.
2. `ApplicationValidatorTest` — красный кейс `""` и guards.
3. `AssessmentServiceTest` — красные кейсы 400 001 / 500 000 / `""` и guards.
4. Прогон `make test`: красные — ровно проектные (падение на ожидаемом
   утверждении или «исключение не брошено»), guards и весь существующий
   набор зелёные. Красный «не по той причине» — баг теста: чинить тест, не
   код. Отдельный коммит с тестами, без правок кода (конвенция «красный тест
   коммитится отдельно от фикса», `tests/Feature/README.md:13`).

Этап 2 — реализация. Тесты этапа 1 не ослабляются.

5. `rules.php`: ключ порога решения (рабочее имя
   `review_mileage_threshold_km`, комментарий о семантике).
6. `DecisionEngine`: сигнатуры
   `__construct(array $thresholds, int $reviewMileageThreshold)` и
   `decide(float $ltv, int $mileage): string` — без значений по умолчанию:
   забытая проводка или аргумент падает громко (ArgumentCountError), а не
   молча, и число 400 000 не дублируется в коде. Проверка пробега — внутри
   approve-ветки: `approve` остаётся только при LTV < 60.0 и пробеге ≤
   порога; ветки review/reject не меняются — приоритет из спеки выполняется
   конструкцией. Докблок дополняется правилом пробега; расхождение «`<=` в
   докблоке vs `<` в коде» при LTV 60.0 не устраняется (спека: не входит).
7. Проводка: `AppFactory:37` передаёт порог из конфига,
   `AssessmentService:33` — `$input['mileage']`. Тем же коммитом
   адаптируются под новые сигнатуры setUp `DecisionEngineTest:17` (порог
   400000 явно, как тестовые данные из AC) и setUp `AssessmentServiceTest:27`
   (порог из реального `rules.php`, зеркально `AppFactory`), а вызовы
   существующего провайдера `DecisionEngineTest:20–38` получают аргумент
   пробега, не влияющий на правило (например 96000). Меняются только вызовы
   и конструирование — не ожидания.
8. `ApplicationValidator`: пустая строка отклоняется до приведения `(int)`
   (после правки `(int)"" === 0` больше не должен пройти валидацию);
   рабочая реализация — сентинел −1 для `""` по пути `null`/отсутствия
   ключа, текст ошибки остаётся существующим. Не использовать `empty()` и
   falsy-проверки: зацепят валидные `0` и `"0"` (ловится guard-тестом 0).
9. Прогон: красные зеленеют, guards и существующий набор остаются зелёными;
   `make lint`. Не проходит тест — правится код; если причина в требованиях
   — остановка и вопрос, тест не трогается (AGENTS.md). Ручной смоук
   `make up` + curl (400 001 → `review`; `""` → 422) закрывает риск проводки
   `AppFactory`, которую юнит-тесты не видят.
10. REQ-MILEAGE-01 (шаги 5–7) и REQ-MILEAGE-02 (шаг 8) независимы — можно
    двумя коммитами в любом порядке; сигнатурная адаптация тестов едет в
    одном коммите со своим продакшен-изменением, чтобы набор не ломался
    между коммитами.

## 3. Тесты

Фикстуры: движок — LTV 50.0 (approve-зона), 75.0 (review-зона), 95.0
(reject-зона); сервис — payload 450000/900000 → LTV 50.0, 675000/900000 →
75.0, 855000/900000 → 95.0 (зеркалит существующие тесты; остальные поля
полезагрузки валидны). Границы LTV 60.0/85.0 не тестируются — вне задачи
(спека: пороги не меняются). Тесты: AAA, имя описывает поведение,
заканчиваются assert'ом (AGENTS.md).

Граница порога решения 400 000 (REQ-MILEAGE-01):

- 399 999 (ниже границы) → `approve` (AC-MILEAGE-01) — guard, зелёный с
  начала; на сервисе `approved_limit` = запрошенной сумме.
- 400 000 (ровно на границе) → `approve` (AC-MILEAGE-02) — guard: граница
  включительна («не больше»); ловит случайную замену строгого сравнения на
  нестрогое в реализации.
- 400 001 (выше границы) → `review`, `approved_limit` = 0 (AC-MILEAGE-03) —
  красный: сегодня `approve`.
- 500 000 (верх рабочей зоны правила) → `review`, `approved_limit` = 0
  (AC-MILEAGE-09) — красный: сегодня `approve`; подтверждает, что правило
  живёт до границы валидации включительно.

Границы валидации 0…500 000 (REQ-MILEAGE-03, существующее поведение):

- −1 (ниже нижней границы) → 422 — guard: «от 0».
- 0 (ровно на нижней границе) → проходит валидацию, нормализуется в 0 —
  guard: ловит `empty()`/falsy-ловушку шага 8.
- 500 001 (выше верхней границы) → `ValidationException` → 422
  (AC-MILEAGE-08) — guard: до `decide()` не доходит.

Пустое значение (REQ-MILEAGE-02):

- `""` (пустая строка) → `ValidationException` с ключом `mileage` → 422, до
  расчёта решения не доходит (AC-MILEAGE-06) — красный: сегодня `""` → 0 км
  → `approve`. Текст ошибки не ассертится (открытый вопрос 2).
- `null` / ключ отсутствует → 422 «Пробег от 0 до 500000 км» (AC-MILEAGE-07)
  — guard: существующее поведение, текст зафиксирован спекой.
- `" "` (только пробелы) и нечисловые строки (`"abc"`) — поведение
  требованиями **не определено** (сегодня `(int)`-приведение даёт 0 км и
  проходит) — тесты не пишутся, пока нет ответа; см. вопрос 3.

Приоритет с другими решениями по заявке (спека закрыла Q1):

- 400 001 + LTV 75.0 → `review`, без изменений (AC-MILEAGE-05) — guard.
- 400 001 + LTV 95.0 → `reject` (AC-MILEAGE-04) — guard: правило не
  понижает `reject`; проверяется на движке и на сервисе.

Слои:

- `DecisionEngineTest` — логика правила: 399 999 / 400 000 / 400 001 /
  500 000 при LTV 50.0; guards (400 001, LTV 75.0 и 95.0).
- `ApplicationValidatorTest` — 422-зона: `""` (красный); `null`, отсутствие
  ключа, 500 001, −1, 0 (guards); ассертится исключение и ключ `mileage` в
  `errors()`; для AC-MILEAGE-07 можно ассертить точный текст, для `""` —
  нельзя.
- `AssessmentServiceTest` — композиция и `approved_limit`: 399 999 →
  `approve` + лимит = сумме (guard); 400 000 → `approve` + лимит = сумме
  (guard, через реальный `rules.php`); 400 001 и 500 000 → `review` + лимит
  0 (красные); `""` → исключение (красный); guards: (400 001, LTV 75.0) →
  `review`, (400 001, LTV 95.0) → `reject`, `null` → исключение, 500 001 →
  исключение.

Итого красных 6: движок — 400 001, 500 000; валидатор — `""`; сервис —
400 001, 500 000, `""`. Остальные кейсы — guards, зелёные с начала: их
назначение — зафиксировать существующее поведение и границы до реализации,
чтобы этап 2 не мог незаметно их сломать. Требование «все новые тесты должны
быть красными» не ставится и вредно: guards красными быть не могут, а
искусственно «краснить» их — значит ломать существующий код ради ритуала.

Соответствие AC: AC-01 — 399 999 (guard); AC-02 — 400 000 (guard); AC-03 —
400 001 (красный); AC-04 — (400 001, LTV 95.0) guard; AC-05 — (400 001,
LTV 75.0) guard; AC-06 — `""` (красный); AC-07 — `null`/отсутствие ключа
(guard); AC-08 — 500 001 (guard); AC-09 — 500 000 (красный). Все девять AC
покрыты, кейсов сверх AC нет (кроме anti-trap guards −1 и 0, защищающих
существующий диапазон «от 0»).

Правила этапа 2 для тестов: тесты этапа 1 не удаляются, не помечаются
skipped, их ожидания не меняются и не ослабляются; единственная допустимая
правка существующих тестов — сигнатурная адаптация конструирования и
вызовов (шаг 7) без изменения ожиданий.

## 4. Риски

- Два порога пробега с разной семантикой (400 000 — решение, 500 000 —
  валидация). Главный риск проводки — передать в движок `max_mileage_km`
  (500000): правило станет мёртвым, потому что всё выше 500 000 отсекается
  валидацией до `decide()`; ловится красным кейсом 400 001 → `review`, а на
  сервисе — тем, что setUp читает реальный `rules.php`. Само значение
  `max_mileage_km`, текст ошибки диапазона и остальные тексты 422 не
  меняются (спека: не входит).
- Проводка `AppFactory` (строка 37) юнит-тестами не покрыта: оба тестовых
  класса собирают граф объектов сами. Неверный ключ в `AppFactory` оставит
  набор зелёным, а прод — сломанным; смягчение — ручной смоук на шаге 9;
  системное решение — feature-тест через HTTP (вне плана, вопрос 4).
- Приоритет с `reject`: спека закрыла вопрос, но остаётся риск реализовать
  «буквальное понижение» — проверка пробега вне approve-ветки понизит
  `reject` до `review` при высоком пробеге. Ловится guard'ом AC-04;
  вложенная проверка исключает ошибку по построению.
- Ловушка `<`/`<=` на LTV ровно 60.0: докблок обещает «`LTV <= approve_max ->
  approve`», код проверяет `<` (расхождение зафиксировано в
  `code_map.md`), спека подтверждает «approve < 60.0» и исключает
  исправление. При правке докблока — не «чинить» LTV-часть и не добавлять
  кейс LTV 60.0: его поведение вне AC, не покрыто существующим провайдером,
  а изменение — бизнес-правка без согласованного требования (AGENTS.md).
- `empty()`/falsy-проверка пустого пробега зацепит валидные `0` и `"0"` —
  ловится guard-тестом 0; проверка `""` обязана идти до `(int)`-приведения,
  иначе `(int)"" === 0` снова пройдёт как 0 км.
- Текст ошибки для `""` не зафиксирован (спека, Open questions 2): тесты к
  тексту не привязываются (исключение + ключ `mileage`); рабочее решение
  переиспользует существующий текст диапазона — если согласуют другой
  текст, правка коснётся только `ApplicationValidator`.
- Имя и место ключа конфига не зафиксированы (спека, Open questions 1):
  рабочее имя `vehicle.review_mileage_threshold_km`; переименование позже —
  три точки правки: `rules.php`, `AppFactory:37`, `AssessmentServiceTest:27`.
- Контракт для прямых API-клиентов: `""` раньше молча проходила как 0 км,
  теперь 422. Фронтенд формы не задет (`Number('') === 0`,
  `frontend/app.js:14`), но клиенты, отправлявшие `""`, увидят новое
  поведение — это и есть согласованное REQ-MILEAGE-02, отдельных действий
  не требует.
- Старые заявки не пересчитываются (спека): решение писалось при создании
