## Замечания

### 1. AC-MILEAGE-09 не покрыт тестом

- Требование: REQ-MILEAGE-01, AC-MILEAGE-09 (пробег ровно 500 000 км при
  approve-LTV → `review`, `approved_limit` = 0) —
  `docs/spec/spec_MILEAGE.md:54–59`.
- Файлы: `tests/Unit/DecisionEngineTest.php`, `tests/Unit/AssessmentServiceTest.php`.
- Доказательство: ни один тест не передаёт пробег 500 000 в `decide()` или
  `assess()` (grep по `500000` в тестах находит только текст ошибки в
  `ApplicationValidatorTest.php:104,121` и `LtvCalculatorTest.php`, к пробегу
  отношения не имеющий). План прямо обещает эти кейсы — «500 000 (верх
  рабочей зоны правила) → review (AC-MILEAGE-09) — красный»
  (`docs/plan/plan_MILEAGE.md:194–196`, список кейсов для движка
  `plan_MILEAGE.md:~239`, для сервиса `plan_MILEAGE.md:~245–247`) — но в
  итоговом diff их нет. Кейс важный: он единственный отличает «правило живёт
  до границы валидации включительно» от случайной передачи в движок
  `max_mileage_km` вместо `review_mileage_threshold_km` (риск из плана
  смягчался именно этим тестом; сейчас при такой подмене набор остался бы
  зелёным, т.к. все пробеги в тестах ≤ 400 001).

### 2. AC-MILEAGE-08 не покрыт тестом

- Требование: REQ-MILEAGE-03, AC-MILEAGE-08 (пробег 500 001 км → HTTP 422) —
  `docs/spec/spec_MILEAGE.md:92–93`.
- Файл: `tests/Unit/ApplicationValidatorTest.php`.
- Доказательство: в файле нет теста с `mileage => 500001` (или иным
  значением выше `max_mileage_km`). На `main` такой тест тоже не было —
  grep по `git show main:tests/...` не находит, так что это не удаление, а
  незакрытый AC, который спека добавила в проверяемые. План обещал:
  «500 001 (выше верхней границы) → ValidationException → 422
  (AC-MILEAGE-08) — guard» (`docs/plan/plan_MILEAGE.md:203–204`) и в сводке
  «AC-08 — 500 001 (guard)», «Все девять AC покрыты»
  (`plan_MILEAGE.md:~255–257`). Promise не выполнено. Косвенно поведение
  видно из кода (`ApplicationValidator.php:46–48`: `$mileage >
  max_mileage_km` → ошибка), но содержательного теста нет — изменение
  верхней границы или сравнения `>` на `>=` осталось бы незамеченным
  (кроме случаев 500 000/500 001, которые как раз не тестируются).

### 3. План обещал guard-кейсы, которых нет в тестах (младшее)

- Требование: не REQ напрямую — расхождение план ↔ тесты по REQ-MILEAGE-02/03.
- Файлы: `docs/plan/plan_MILEAGE.md` (раздел тестов), тесты.
- Доказательство: план обещал в `AssessmentServiceTest` guard'ы «`null` →
  исключение, 500 001 → исключение» и в `ApplicationValidatorTest` guards
  «−1, 0» (ловушка falsy/`empty()` при проверке пустой строки,
  `plan_MILEAGE.md:~207–212, 243–247`). В diff этих тестов нет: нет кейса
  `mileage => 0` (защищает от зацепленной `empty()`-проверки, которая
  сломала бы валидный пробег 0), нет сервисного `null`. AC-07 при этом
  покрыт на валидаторе (`testRejectsNullMileage`,
  `testRejectsMissingMileageKey`), так что на уровень AC это замечание не
  влияет — только на расхождение с планом и на оставшуюся без guard'а
  falsy-ловушку.

## Что проверено и подтверждено

- **AC-MILEAGE-01/02/03** — покрыты и на движке
  (`DecisionEngineTest.php:41–53`), и на сервисе
  (`AssessmentServiceTest.php:75–99`): 399 999 → `approve` (лимит = сумме),
  400 000 → `approve` (включительность границы), 400 001 → `review`,
  `approved_limit` = 0.
- **AC-MILEAGE-04** — `testKeepsRejectWhenMileageAboveThresholdAndLtvAboveReviewMax`
  (оба слоя): 400 001 + LTV 95.0 → `reject`. Реализация вкладывает проверку
  пробега внутрь approve-ветки (`DecisionEngine.php:36–40`), поэтому
  `reject`/`review` не понижаются — приоритеты решений из интервью
  соблюдены.
- **AC-MILEAGE-05** — 400 001 + LTV 75.0 → `review` без изменений (оба слоя).
- **AC-MILEAGE-06** — `""` → `ValidationException` с ключом `mileage`:
  `ApplicationValidatorTest.php:86–94` (валидатор) и
  `AssessmentServiceTest.php:121–126` (сервис — «до расчёта не доходит»).
  Текст ошибки не ассертится — корректно, это открытый вопрос 2 спеки.
- **AC-MILEAGE-07** — `null` и отсутствие ключа → 422 с точным текстом
  «Пробег от 0 до 500000 км»: `ApplicationValidatorTest.php:96–125`.
- **Лишние требования** — не обнаружены: в diff нет изменений фронтенда, БД,
  формы ответа API, порогов LTV, `max_mileage_km` (500 000 сохранён,
  `rules.php:23`), текстов 422; порог 400 000 вынесен в отдельный ключ
  `vehicle.review_mileage_threshold_km` (`rules.php:27`) — как и обещал план.
- **Ослабление тестов** — не обнаружено: существующие ожидания не менялись;
  единственная правка старых тестов — сигнатурная адаптация
  (`decide($ltv)` → `decide($ltv, 96000)`, конструктор движка в setUp,
  `payload()` с параметром `mileage`), ожидания прежние. Guard-провайдер
  LTV в `DecisionEngineTest` сохранён.
- **Согласованность с `max_mileage_km` и приоритетами** — реализация читает
  `review_mileage_threshold_km` (400 000) для решения и оставляет
  `max_mileage_km` (500 000) для валидации; `AppFactory.php:37` передаёт
  правильный ключ. Проверка строгая (`$mileage > threshold`), граница
  400 000 включительна, что соответствует «не больше 400 000 км».

## Ограничения проверки

- Unit-тесты вызывают доменные классы напрямую; AC-06/07/08 сформулированы
  через HTTP 422, а feature-тестов через HTTP нет (в `tests/Feature/` только
  README) — маппинг «ValidationException → 422» проверен по коду
  (`AppFactory`/обработчик ошибок), не тестом. План это ограничение
  декларирует сам (открытый вопрос 4).
- Проводка `AppFactory` (ключ `review_mileage_threshold_km`) юнит-тестами не
  покрывается (обоих тестовых setUp'ов каскад строится вручную) — риск
  признан в плане, смоук через HTTP в рамках проверки не выполнялся.
- Поведение `" "` и `"abc"` в поле пробега намеренно не определено и не
  тестируется (открытый вопрос 3 плана) — `(int)`-приведение даёт 0 км,
  тест не утверждает обратное.
- `make lint` не запускался (проверка только чтением и `make test`);
  синтаксическая корректность подтверждается прогоном PHPUnit.

## Итог

Реализация соответствует intent/spec, приоритеты решений и
`max_mileage_km` не задеты, тесты не ослаблены. Два AC из спеки (08, 09)
не покрыты тестами, несмотря на прямое обещание плана; ещё три
guard-кейса из плана (пробег 0, −1, сервисный `null`/500 001) отсутствуют
без ущерба для покрытия AC, но guard от falsy-ловушки (пробег 0) планом
предусматривался и не создан.

## Где агент Minimax M3 срезал угол

Агент, реализовавший тесты и код фичи про пробег, проверил основные
случаи 399999 / 400000 / 400001 и пустой пробег, но не полностью
покрыл тестами согласованную спецификацию и план.

По результатам проверки отсутствуют тесты для двух критериев приёмки:
AC-MILEAGE-09 — пробег ровно 500000 допускается валидацией и при
LTV для approve приводит к review с нулевым лимитом;
AC-MILEAGE-08 — пробег 500001 отклоняется валидацией.
Также не добавлены предусмотренные планом проверки пробега 0 и -1.

Таким образом, зелёный make test подтвердил прохождение написанных
тестов, но не полное покрытие требований. Проверку соответствия
каждого REQ/AC конкретному тесту пришлось выполнить отдельно.

При этом ослабления существующих тестов не обнаружено: изменения
вызовов DecisionEngine соответствуют новой сигнатуре, ожидаемые
результаты сохранены. Для завершения работы нужно добавить
пропущенные проверки и повторно запустить тесты.
